前言

　　最近做了一个叫「天工」的桌面端应用（感觉现在有一堆叫「天工」的产品🤣）给我司的运营支持团队提效，他们每个人都负责运营一些商户，日常在美团的开店宝后台有两块比较耗时的工作：

  1. 对好评进行回复（从话术库中随便挑一条回复即可，不千篇一律就行）；
  2. 下载三类报表（经营参谋、推广通、门店评价）并上传到公司内部系统。

　　天工诞生的初衷就是把这些重复操作自动化，帮他们提高人效，让他们人均能接管更多商户。

　　这是我第一次接触 Electron 和 Puppeteer，整个开发过程都是和 Cursor & Claude Sonnet 4 协作完成的，当时团队正好刚开始全面推广 AI Coding，需要量化提效成果，下面这两张图是当时的记录：

　　在 Cursor 和 Claude 的加持下，第一版下载链路只花了一个下午就跑通了。看着 Electron 窗口自动跳转页面、选择日期范围、勾选指定指标、等待 loading 结束、点击下载按钮、把报表 Excel 下载到 Download 里的指定文件夹——运营平日里要花好几个小时去重复干的活，脚本几十秒就跑完了，那种感觉简直妙不可言！

　　内测期间，试用的几位运营完全是把天工当宝贝，每天都在高强度使用，反馈了一大堆边界 case 和体验问题。这个月月初，团队 leader 在群里进行了一个表扬：79 个账号，3 天的经营参谋数据，只用了 17 分钟！

　　看到这些反馈的时候，那种 sense of achievement 真的拉满了。但 drama 的是，天工刚全量推广没多久，这位 leader 和整个运营支持团队就被优化了……这个工具最终替代的，恰恰是这群帮我们打磨它的人。

　　天工毫无疑问是一次非常成功的业务提效实践，写下这篇复盘，除了记录这个工具从零搭起来的工程细节，也是为了纪念这支曾经和我们并肩走过这段路的运营支持团队。在公司的组织架构里，他们或许只是被打上“已离职”标签轻描淡写翻过的一页，但在天工的来时路上，他们是绝对绕不开的战友与同行者。

2026.2.2 更新

　　今天公司开年会，在 CEO 捷哥的年度成果汇报里，天工也有幸占有了一隅。在台下看到 55 万这个数字的时候还挺恍惚的，当初一下午跑通的脚本，下载量居然到了几十万的量级。天工也是我获得年度优秀员工的重要原因，放几张照片留个纪念～

天工长什么样

　　天工有四个菜单项：

多账号管理与本地状态存储

　　要让天工开始干活，首先要登录美团开店宝账号。

多账号隔离：一个 partition 配置就够了

　　每个运营手里都有几十个开店宝账号，不可能每次切账号都让他们重新登录，所以第一步得先解决登录态保持 & 隔离的问题。

　　一开始我以为要自己去写一套代码维护 Cookie 和本地存储，但是让 AI 调研了一下，发现 <webview> 标签的 partition 属性似乎天然就支持会话隔离。

　　于是我立刻写了个 demo 试了一下，分别在 account-1 和 account-3 登录不同门店，account-2 保持未登录，来回切了几次，各自的登录态居然真的互不干扰：

　　本来我都做好要写一堆复杂逻辑的预期了，结果一个 partition 配置就把这个核心需求点跑通了，这种四两拨千斤的感觉真的让人着迷～

　　还有个很有意思的小插曲，在我把 demo 发到群里之后，后端开发友哥也来私聊问我这个账号隔离是怎么这么快实现的：

　　其实核心代码就这么几行——给每个账号的 <webview> 配上独立的 partition 和 key：

　　通过 partition 配置，Chromium 底层会把不同账号 <webview> 的 Cookie 和 LocalStorage 在内存里自动隔离，如果再加上 persist: 前缀，数据就会写到本地磁盘持久化存储，下次重新打开天工也可以直接复用登录态了。

　　key 也是有说法的，<webview> 的 partition 一旦生效就无法动态修改，所以这里还需要借助 React 的 key 机制，在切换账号的时候重新创建 <webview> 实例。

    A --> PA["persist:account-a
A 的专属 Cookie 与 LocalStorage"]
    B --> PB["persist:account-b
B 的专属 Cookie 与 LocalStorage"]
    PA --> VA["webview (账号 A 登录态)"]

MobX 与 electron-store 的状态持久化

　　除了开店宝的 Cookie，天工自己也有东西要存——账号列表、当前选的是哪个账号、还有导入的话术。

　　每次改完状态都手动存一下？太容易忘了。所以用 reflect-metadata + 装饰器 + MobX + electron-store 搞了一套自动持久化：

基类 PersistStore 会找到所有打了 @persist 的字段：

  1. 启动时从 electron-store 读数据回填到 MobX store。
  2. 用 MobX 的 reaction 监听变化，值变了就自动写回去。
sequenceDiagram
    participant App as 应用启动
    participant AS as Account Store
    participant PS as PersistStore
    participant Ref as 反射 API
    participant MobX as MobX
    participant Store as electron-store
    App->>AS: new Account()
    AS->>PS: super() 调用父类构造函数
    PS->>PS: setTimeout(() => {...}, 0)
    Note right of PS: 延迟到下一个事件循环
    AS->>AS: makeObservable(this)
    PS->>Ref: getPersistKeys()
    Ref-->>PS: 返回 ['accountList', 'currentAccountId']
    PS->>Store: loadPersistedData()
    Store-->>PS: 返回存储的数据
    PS->>AS: 设置属性值
    PS->>MobX: setupReactions()
    MobX-->>PS: 为每个属性设置 reaction
    Note over PS: 初始化完成，开始监听变化
    App->>AS: setCurrentAccount('account-123')
    AS->>AS: 修改 currentAccountId
    MobX->>MobX: 检测到变化
    MobX->>MobX: delay 等待 300ms
    MobX->>Store: 自动保存到 electron-store
    Note right of Store: 数据持久化完成

　　加了 300ms 的 delay，连着改的时候不会疯狂写盘：

　　这里监听的是 this[key]，账号列表更新时会替换数组引用，能触发 reaction。读写都收在基类里，业务代码就不用管存盘了——不过嵌套对象如果原地修改，不一定能被捕获到。

账号信息的导出与导入

　　账号都登录好了，但另一位同事也要用这些账号怎么办？总不能让人家再扫一遍码吧。

　　前期的做法比较朴素：直接导出 Partitions 目录，在另一台电脑导入，顺便把天工的账号列表也同步过去。

　　主进程用 app.getPath('userData') 拿到路径，剔除 Cache、Code Cache 这些没用的目录后打包到桌面；另一边用 commander + chalk 做了个导入 CLI，走一遍大概是这样：

过滤无用 Cache"]
    E --> D["桌面的账号数据文件夹"]
    D --> I["同事 B 执行导入 CLI"]
    I --> P["写入 B 电脑的 Partitions 目录"]
    P --> S["同步 electron-store 账号列表"]
    S --> B["打开天工，确认导入账号的登录态"]

　　导入时支持先用 --dry-run 预览，确认没问题再真正写入：

　　用法就是先集中扫码登录，然后导给同事。不过目录复制成功不代表登录态还在，导入后还是得实际打开确认一下。

　　看看天工怎么干这事：

　　右侧勾选话术、点击「开始回复」，左侧开店宝的回复框就会自动展开并轮换填入。这一版把「发布」按钮留给人工——话术填好后还是要自己点一下发布。

Excel 话术导入与进程通信

　　话术是 Excel 表格，点「导入话术」会弹文件选择框，选完读取解析。文件选择和 Excel 解析都放在主进程，页面通过 preload 暴露的接口用 IPC 调：

sequenceDiagram
    participant UI as React 页面
    participant P as preload
    participant M as Electron 主进程
    participant F as 系统对话框 / Excel
    UI->>P: 调用 window.tiangong.importScripts()
    P->>M: ipcRenderer.invoke('excel-import')
    M->>F: dialog.showOpenDialog()
    F-->>M: 返回选中的本地文件路径
    M->>M: xlsx.readFile() 解析每个 Sheet
    M-->>P: 返回结构化的话术数据
    P-->>UI: Promise resolve 数据
    UI->>UI: 写入 MobX store 并持久化

　　主进程按 Sheet 组织话术，读每行第一列文本，返回给页面保存。这里是 invoke / handle，页面主动问主进程要数据；到了后面下载报表就反过来了，主进程主动 push 进度给页面。

从 webContents 定位 Puppeteer Page

　　自动化填写用 puppeteer-in-electron 连接 Electron 内置的 Chromium，让 Puppeteer 来操作页面。

　　但有个问题：React 这边只知道 webview 的 webContentsId，Puppeteer 操作的是 Page 实例，怎么对上？

　　想了个很土但很好使的方案：往目标 WebContents 注入一个 GUID，再遍历 Puppeteer 的所有 Page，找到包含这个 GUID 的那个：

flowchart TB

    W --> G["向页面注入唯一 GUID 标记"]
    G --> T["枚举 Puppeteer 的 targets"]
    T --> P["匹配到 GUID 相同的 Page 实例"]
    P --> F["定位到美团评价的 iframe"]
    F --> R["查找未回复评价的回复框并填入话术"]

自动填写与输入事件处理

批量下载报表

　　当时每位同学平均管 120 家门店。周一周二下「经营参谋」和「推广通」，周四周五下「门店评价」。每个门店都要手动切进后台、选日期、勾指标、提交、等生成、再去列表里一个个点下载。每周重复几百上千次，算了一下每人每周花 5~6 小时在这上面。

　　天工做的就是把这些操作自动化，支持经营参谋、门店评价、推广通三类报表的批量下载。

下载条件配置与账号任务调度

　　用起来很简单，选好报表类型和日期、勾上要下的账号，点开始就行。

　　前期版本的账号循环放在渲染进程的 useDownloadManager 里：每次通过 IPC 把账号、报表类型、日期和任务 ID 丢给主进程，等这个账号跑完再处理下一个。主进程只管单个账号的网页操作和文件下载。

sequenceDiagram
    participant U as React / useDownloadManager
    participant S as downloadTaskStore
    participant M as 主进程下载服务
    participant B as 开店宝后台页面
    U->>S: 初始化主任务与账号子任务
    S-->>U: 返回任务 ID
    loop 依次处理选中账号
        U->>S: 标记该账号为运行中
        U->>M: 经 IPC 传入账号、日期、任务 ID
        M->>B: 启动后台窗口执行 Puppeteer 下载策略
        Note over M,B: 切换平台 -> 勾选指标 -> 生成报表 -> 触发文件下载
        M-->>U: 返回该账号处理结果
        U->>S: 更新账号任务状态
    end
    U->>M: 调用系统桌面通知

　　虽然发起的是一批账号，底层还是一个个跑。进度去「下载中心」看就行，不用一直盯着。

隐藏窗口与登录态复用

　　批量任务要依次跑几十个账号的后台，总不能一个个弹窗口出来。所以主进程会开一个 show: false 的隐藏 BrowserWindow，Puppeteer 在后台悄悄干活，partition 复用前台登录好的：

persist:account-a"]

    H["后台隐藏 BrowserWindow

连接 Electron 驱动页面"] --> H

　　前台后台用的是同一份登录态，跑完销毁窗口就行。

报表生成、下载与文件归档

　　以最繁琐的经营参谋为例，它还分美团和点评两个子平台：

flowchart TB
    A["打开后台经营参谋页"] --> B["等待表单渲染完成"]
    B --> C["切换美团 / 点评平台"]
    C --> D["选定日期区间并全选指标"]
    D --> E["点击「立即下载」提交生成任务"]
    E --> F["确认弹窗并进入下载列表"]
    F --> G["等待生成完毕，绑定下载上下文"]
    G --> H["触发最终下载按钮"]
    H --> I["主进程拦截下载流保存至本地"]

　　这里有个坑：点「立即下载」并不会直接给你文件，它只是触发平台异步生成报表，得等列表里出现对应记录后再点一次，才能真正下载。

　　而且下载列表里还混着以前生成的报表，不能看到「下载」按钮就直接点——得先核对文件名里的日期对不对，如果还在生成中或日期不一致，就刷新重试。

　　还有个问题：浏览器触发下载的时候只知道”我要下一个文件”，但天工得知道这个文件是哪个任务的、哪个账号的、美团还是点评。所以在点下载按钮之前，会先设一个下载上下文（Download Context），把任务 ID、账号、平台、日期都带上。拦截器拿到下载请求时读这个上下文，就知道该怎么命名和归档了：

sequenceDiagram
    participant P as 下载策略
    participant D as downloadInterceptor
    participant F as 本地文件系统
    participant U as React 任务界面
    P->>D: 预先设置上下文 (主任务ID、账号、平台、日期)
    P->>P: 点击列表里的下载按钮
    D->>D: 捕获下载请求，读取上下文
    D->>U: 通知创建 FileTask 进度条
    D->>F: 流式写入本地指定目录
    F-->>D: 文件落盘成功
    D->>U: 更新该文件的下载状态

下载任务的状态管理与问题排查

　　哪些账号下好了、哪些挂了、挂了的怎么重试——都在「下载中心」里看。

主任务、账号任务与文件任务

　　任务拆成三级：主任务（MainTask） -> 账号任务（AccountTask） -> 文件任务（FileTask）。

flowchart TB

批量下载经营参谋报表"]

部分成功与失败账号重试

　　一个账号可能有好几个文件要下。比如美团的报表下好了，点评的超时了——这个账号就不能简单标”成功”或”失败”，所以多了一个「部分成功」状态。

　　重试的时候会把失败和部分成功的账号收集起来，沿用原来的配置再跑一轮，已经成功的就跳过。

　　不过重试粒度是账号级的，没有细到只补某个失败文件，所以部分成功的账号里已经下好的报表可能会再下一次。

The End

　　做提效工具的工程师往往有一种天然的道德满足感：我们坚信自己是在把人从枯燥的重复劳动中解放出来，让他们能够去做更有价值的事情。但在追求极致降本增效的浪潮里，“从重复劳动中解脱”与“失去工作”，或许只有一步之遥。

　　回看整个开发过程，我自己也是在 Cursor 和 Claude 的加持下，才以一种过去难以想象的速度把这套系统搭建出来的。今天我作为程序员，拿 Claude 做杠杆，亲手完成了对一个业务团队的替代，但在效率狂飙的浪潮里，我自己又处在什么位置呢？

　　如今大模型和 Agent 的能力日新月异，从代码补全到自主调度、从多模态推理到直接操控设备，写代码这件事本身的“不可替代性”正在被一层层剥离。我们今天在屏幕前用提示词让 AI 拆需求、写业务、修 bug，但我们的每一次提问、纠正和采纳，其实也在源源不断地变成大模型进化的训练集，这何尝不像当初那群在群里热情帮我们扫雷找各种边界情况的运营伙伴呢？

　　没有人是一座孤岛，如果提效的终局是消除冗余，那么在不远的将来，当大模型也能算无遗策地端到端交付系统时，我们这些亲手把缰绳交出去的程序员，又会在哪一天以同样体面而平静的方式，迎来属于自己的“优化”呢？
